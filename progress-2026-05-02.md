# Project Progress Update

**Date:** 2026-05-02  
**Author:** Jayaprakash Sivanandam

For my project, I have moved from design into a working end-to-end build. My original plan in the project description used LangGraph orchestration, but while implementing I shifted to building a multi-agent system using the A2A protocol. I made that change deliberately to achieve cleaner architectural boundaries between agents and to enable a practical deployment model where each node runs as its own independent HTTP service. This has given me true decoupling and horizontal scalability at the cost of added complexity in coordination.

Right now I have six agents wired and running in the notebook flow: router, schema-fetcher, performance analyzer, security auditor, style reviewer, and orchestrator. The router classifies input as SQL query, stored procedure, or unknown. If the input is a stored procedure, I call schema-fetcher to retrieve DDL and extract executable ETL SQL. If the input is a raw SQL query, I skip fetch and go straight to analysis. I run performance, security, and style analysis in parallel, then the orchestrator synthesizes everything into a structured FindingsReport.

I also completed the main tool integration pattern. Instead of LangGraph-bound tools, I now use an MCP server layer with explicit tool calls like get_snowflake_ddl and extract_etl_code_from_ddl. This has made the separation clearer between orchestration and Snowflake/tool logic. I have Pydantic models in place across routing, schema fetch, analyzers, and synthesis so outputs stay structured and predictable.

On prompt and skills management, I now serve prompts through an MCP server layer (a deviation from the original plan), but they continue to live in the skills folder for easy maintenance and versioning. This centralized MCP approach makes prompt delivery consistent across all agents without requiring each agent to parse the filesystem independently, while keeping the source of truth in the skills directory. This design keeps updates simple without touching core orchestration code each time. I am also using model specialization across the flow, with Gemma handling most analyzer workloads and Claude Opus handling synthesis.

My main remaining gap is DDL tool-calling reliability. The schema-fetcher currently uses a ReAct loop with tool discovery and invocation, and this is still the weakest part of the pipeline. I need to harden it so GET_DDL succeeds consistently and edge cases are handled cleanly, especially invalid identifiers, missing procedure signatures, and response normalization.

The second gap is security hooks. I have a working security-auditor agent, but I still need to implement the broader security hook layer I planned, including pre-LLM secret checks and consistent enforcement hooks across nodes. In short, the architecture and core pipeline are working, but my next push is reliability and guardrails.

My current status is that the project is functionally built, the LangGraph-to-A2A deviation is complete and stable at the architecture level, and I am now in the hardening phase focused on DDL tool-call fixes and security hook completion.
